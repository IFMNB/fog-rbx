# Types construction

Эта статья по сути представляет исследование текущего на 26.07.22 число (22.07.2022) поведение типизатора.

Общие типовые конструкты для `object` наследников проектируются через его стандартный шаблон `object.class<>`. По сути, каждый созданный таким образом тип это `intersection`. Далее об этом будет подробнее.

Вообще, все данные из этого гайдлайна указываются в стандартной документации на сайте `luau.org`, и вы можете самостоятельно изучить и прийти к полностью таким же выводам. Этот же гайд предназначен для прояснения "почему так". Кроме того, поведение типов на разных платформах от VSCode платформах не гарантируется. Для подтверждения всех этих теорий использовался LuauLS (LLS), причем с поведением, залоченным на `roblox` тип, а также с `--!strict` проверками типов.

## Variants of type hierarchy

Для начала, самый важный тип который используется в типизации, является тип из `object.class`, который имеет такую конструкцию:

```luau
    type base = typeof(class) -- очевидно object
    export type class <parent = base, that = {}> = that & parent
```

В наследовании линий типов Luau всегда существовала огромнейшая дыра в развитии по сравнению с другими языками где такое возможно. Поэтому в языке для типизационной среды на текущий момент написания этого гайдлайна существует всего 2 простых и ультимативных способа наследоваться: `interserction` и `__index`. 

Дополнительно существует наследование согласно `type function` и его `types` библиотеки. Однако это не является темой гайда, потому что все проверки были созданы с учетом авто-вывода типов на основе кода. Это нужно для того, чтобы избежать и так неимоверный технический долг по поддержке комментариев, самих типов или еще чего-либо нового. Кроме того, это отдельная тема для гайда.

Однако пару слов об этом стоит оставить: `type function` никогда не возвращает корректный тип, после преобразования всегда теряя некоторые полезные данные внутри данных, которые она хранит или описывает или обрабатывает. Например, это неизбежно приводит к потере имен аргументов и комментариев.

### "intersection"

Интерсекция - соединение типов друг с другом, которое удовлетворяет задачам обоих типов. С таблицами это работает как нельзя кстати, потому что структуры соединяются вместе и образуют единый тип, отвечающий сразу всем требуемым интерфейсам. Когда речь заходит о наследовании таких объектов влияние оказывает порядок наследования в котором применяется эта языковая возможность. 

Например:

```luau
    type class <that = {}, parent = base> = that & parent
```

Предоставленный первым `that` будет перезаписывать некоторые поля `parent`. Это работает и в обратную сторону, если переставить местами типы дженерики. Однако, все функции, которые имеют отличия в семантике хотя-бы немного будет невозможно вызывать, поскольку указать точный тип возврата уже не получится. Интерсекция, в отличие от `__index`, не может оверрайдить сигнатуры функций в порядке в котором они установлены, поскольку иначе они не будут удовлетворять другой тип. Следующий тип `C` будет нельзя корректно вызывать, потому что типизатор не сможет выявить корректный исходящий тип:

```luau
    type A = {
        foo: (number) -> number
    }

    type B = {
        foo: (string) -> string
    }

type C = A & B
```

Если бы в `Luau` была реализована автоматическая `type()` проверка на разницу передаваемых значений, и их ожидаемых собственно, а также ожидалось что хэш-таблицы могли бы хранить одни и те же имена и различать их по типам значений - это бы работало. Однако этого никогда не будет из-за природы работы таблиц языка.

Таким образом, чтобы работала интерсекция с динамическими конкретизациями generic-ов, требуется использовать этот метод в паре с `__index`.

Пример невалидного типа:

```luau
    type class <T = {[string]: any}> = object.class<{
        class: T,
        add: <U> (self: unknown, to: metamethods & U, f: methode<T>) -> (),
        remove: <U> (self: unknown, from: metamethods & U, f: methode<T>) -> (),
        set_main: <U> (self: unknown, to: metamethods & U, f: methode<T>?) -> ()
    }, typeof(class)>
```

Это невалидная конструкция, поскольку все перечисленные функции в этом типе будут отличаться от `typeof(class)` и не будут его удовлетворять. То есть, если примерная функция `:add()` ожидает в себе один порядок аргументов, то типизатор при попытке привести это к удобному типу просто не сможет это осуществить, потому что `parent :add() ~= that :add()`. 

### "__index"

Индекс-наследование основано на прототипировании метатаблиц через специальное поле `__index`. Суть данного метода проста: вызвать функцию или просмотреть в таблице нужный элемент, а затем вернуть его.

Проблемой этого метода считается отсутствие структурной надежности в типовом анализе. Получившийся тип не определяет его поддержку всеми другими подтипами в линии, потому что он слишком сложный для текущего анализа и противостоит отношению типизатора к метатабличным `__index` полям, так как он считает их рантайм-заменимыми. Возьмем в пример это:

```luau
    local a = {}
    setmetatable(a, {__index = class})

    type a<T = {[string]: unknown}> = object.class<class<T>, typeof(a)>

    a.f = {}

    local function foo (t: a)

    end

    local r : class
    local d : a
    foo(r)
    foo(d)
```

По иерархии мы знаем, что `a` индексированием наследует `class` и имеет собственные поля, которые могут оверрайдить значения родителя. Этого мы узнали и добились в `intersection`. Однако, `foo(r)` и `foo(d)` никогда не будут совместимы. Почему? Вспомним пройденное.

Основная причина существует в сигнатуре самого типа. Когда мы объявляем тип интерсекционным, для всех значений в паке интерсекций типизатор проверяет, что значения совпадают, либо перезаписывает их согласно порядку передачи типов. Это можно было наблюдать в объявлении `object.class`, там видно, что идет такая цепь: `that & parent` - приоритет отдается `that`. Это в свою очередь позволяет перезаписать синглтоны. Например, наследование от базового `object` имеет `object.class .type == "object"` синглтон, однако `that` разрешит перезаписать его, если только мы укажем явно свойством нового класса-наследника в его типе, что он записывает `.type` иначе, чем `object`. Такое поведение, как мы знаем, работает иначе с функциями.

Суть индексации в том, что она идеально хорошо ложится на поиске прототипированного значения. Мы знаем, что если в точке `A` нет нужного `T`, он будет искаться в `B`. Однако, как известно, типизатор не рассматривает `__index` как надежный источник. Значит, типизатор проверяет полную и четкую сигнатуру типа. Именно здесь кроется проблема: рекурсивные самораспаковывающиеся типы, которые являются `union` того или иного значения не поддерживаются языком, а помимо этого сам `union` требует доказать приведением, что он является конкретным типом. Это запрещает типизатору подтверждать схожесть между типами `A` и `B` в методах, где сигнатура `B` ожидает `B`, а значит туда по идее должен был бы войти и `A` как наследник `B` . Это работает на всю цепь наследования. Значит, даже самый высший базовый класс будет в таком случае несовместим с предком.

### "InterIndex"

Возьмем в пример значения из `intersection`. Там мы имели проблему с правилом разрешения конфликтов неодинаковых по сигнатуре функций. Для того, чтобы решить этот вопрос, мы должны объединить это с `__index`.

```luau
    type class <T = {[string]: any}> = object.class<setmetatable<{
        class: T,
        add: <U> (self: unknown, to: metamethods & U, f: methode<T>) -> (),
        remove: <U> (self: unknown, from: metamethods & U, f: methode<T>) -> (),
        set_main: <U> (self: unknown, to: metamethods & U, f: methode<T>?) -> ()
    } & metas<T>, {__index: typeof(class)}>>
```

Эта конструкция полностью удовлетворяет перезапись указанных функций. Но она неспособна к стабильной жизни, поскольку интерсекция ее подтаблицы заставляет ее возвращать несовместимый с `unknown` тип. Это, вероятно, баг, либо особенность, которую можно воспроизвести только в методах объектов, так как пример далее не воспроизводит проблему:

```luau
    type a = setmetatable<{a: number} & {b: number}, {__index: {r: string}}>
    local f : unknown
    local b = f -- OK
```

Из-за этого невозможен каст `self :: class`, и постоянно возникают ошибки потери типовой информации. Самая стабильная конструкция, по итогу преобразований, будет выглядит так:

```luau
    type class <T = {[string]: any}> = object.class<setmetatable<{
        class: T,
        add: <U> (self: unknown, to: metamethods & U, f: methode<T>) -> (),
        remove: <U> (self: unknown, from: metamethods & U, f: methode<T>) -> (),
        set_main: <U> (self: unknown, to: metamethods & U, f: methode<T>?) -> ()
    }, {__index: typeof(class)}>>
```

Почему? Потому что `setmetatable<child, { __index: parent }>` моделирует не `intersection`, а иерархический поиск членов. Разберемся подробней.

#

#### Issue #2171 — Metatable `__index` не поддерживает пересечения типов

Проблема заключается в том, что New Solver некорректно работает с типом, находящимся в `__index`, если он представляет собой `intersection`. При объявлении метатаблицы вида

```luau
setmetatable({}, {
    __index = A & B
})
```

типизатор перестаёт согласованно обрабатывать поиск членов. При обращении к полю, которое существует только в одной из частей пересечения, он одновременно способен вывести правильный тип этого поля и при этом сообщить, что такого поля не существует. Иными словами, механизм поиска членов через `__index` и механизм вывода типа работают независимо друг от друга и приходят к взаимоисключающим результатам.

Фактически это означает, что анализатор не рассматривает `intersection` внутри `__index` как единый источник членов. Вместо объединения всех доступных полей поиск завершается преждевременно, из-за чего часть структуры оказывается недоступной, несмотря на то, что информация о ней сохраняется внутри самого типа. Это приводит к невозможности использовать `intersection` как способ объединения нескольких прототипов через метатаблицу. ([Luau][1])


#### Issue #2219 — Статически известные поля из `__index` не участвуют в построении структуры типа

Данная проблема является более общим проявлением ограничений анализа метатаблиц. Даже если цепочка `__index` полностью известна во время анализа и состоит исключительно из статически определённых таблиц, типизатор не включает их поля в результирующую структуру объекта.

В результате таблица обладает всей необходимой информацией для поиска членов во время выполнения программы, однако система типов рассматривает только собственные поля объекта и игнорирует все поля, доступные через цепочку `__index`. Из-за этого обращения к существующим членам сопровождаются сообщениями об отсутствии ключа, хотя весь путь поиска известен заранее и не содержит никакой динамики.

По сути, текущий анализ рассматривает `__index` лишь как дополнительную информацию о метатаблице, но не использует её для построения полного структурного представления типа. Это существенно ограничивает применение прототипного наследования при строгой типизации. ([Luau][1])


#### Issue #2578 — Потеря информации о метатаблице после преобразования типа

Эта проблема проявляется после выполнения операций над уже существующим метатабличным типом. Если тип `setmetatable<T, ...>` используется напрямую, поиск членов через `__index` выполняется корректно. Однако после участия этого типа в некоторых преобразованиях, например в пересечениях или после применения отрицания `~nil`, механизм поиска перестаёт учитывать содержимое метатаблицы.

При этом сам тип продолжает содержать информацию о наличии метатаблицы — она отображается в выводе анализатора, а значит не была потеряна при построении типа. Теряется именно возможность использовать эти сведения во время разрешения членов. В результате два логически эквивалентных типа начинают вести себя по-разному исключительно из-за того, что один из них прошёл дополнительный этап нормализации.

Это указывает на несогласованность между внутренним представлением типа и алгоритмом поиска членов: информация о метатаблице сохраняется, однако после некоторых преобразований больше не участвует в разрешении свойств объекта. ([Luau][1])

Эти три проблемы напрямую касаются механизма обработки __index, однако они не затрагивают приведённую конструкцию по одной причине: в ней __index используется только как источник отсутствующих членов, а не как средство формирования основной структуры типа.

```luau
type class<T = {[string]: any}> = object.class<
    setmetatable<{
        class: T,
        add: ...,
        remove: ...,
        set_main: ...
    }, {__index: typeof(class)}>>
```

Здесь тип, передаваемый в `setmetatable`, уже содержит полную собственную структуру объекта. Все методы, сигнатуры которых необходимо переопределить `:add()`, `:remove()`, `:set_main()`, объявлены непосредственно в таблице. Поэтому при обращении к этим членам типизатор находит их ещё на первом этапе поиска и не использует `__index`. Метатаблица начинает участвовать только тогда, когда собственного поля не существует.

Именно поэтому `Issue #2171` не проявляется. Он возникает только тогда, когда сам `__index` должен объединять несколько структур через `intersection`. В рассматриваемом типе этого не происходит: `__index` содержит единственный тип `typeof(class)`, а все конфликтующие члены уже определены локально.

По той же причине не проявляется `Issue #2219`. Этот баг связан с тем, что типизатор не включает поля из `__index` в структурное описание объекта. Однако рассматриваемый тип не зависит от этого поведения для собственных методов. Единственное, что требуется от `__index`, — предоставить доступ к отсутствующим членам базового класса. Даже если эти поля не становятся частью основной структуры типа, локально объявленные методы уже полностью описывают интерфейс наследника.

`Issue #2578` также не влияет на данную конструкцию. Он возникает после преобразований метатабличного типа, когда информация о наличии `__index` сохраняется, но перестаёт использоваться при разрешении членов. В рассматриваемом случае тип `setmetatable<...>` не подвергается дополнительным преобразованиям, которые изменяют его внутреннее представление. Он сразу передаётся в `object.class`, где участвует только как левый операнд внешней `intersection`. В результате информация о метатаблице остаётся доступной для поиска отсутствующих членов.

Именно поэтому конструкция оказывается устойчивой. Она не требует, чтобы типизатор умел строить структурное объединение по `__index`, не использует `intersection` внутри самого `__index` и не заставляет анализатор разрешать конфликтующие сигнатуры через механизм поиска членов. Все потенциально конфликтующие методы объявлены непосредственно в собственном типе таблицы, а `__index` выполняет лишь свою естественную роль прототипного поиска для тех членов, которые наследник не переопределяет.

`setmetatable<child, { __index: parent }>` не преобразуется типизатором в `child & parent`. Это отдельный вид `table type`, который хранит собственную структуру таблицы и дополнительную информацию о разрешении членов через `__index`. При поиске членов сначала используются собственные поля таблицы, а `__index` рассматривается как источник отсутствующих членов. При этом такой тип всё ещё может участвовать во внешней `intersection`, если он передан в `object.class<>`. Собственные поля `child` имеют приоритет, а `parent` используется как резервный источник отсутствующих членов. Именно поэтому данная конструкция работает и не нарушает правила обоих вариаций типового шва. Причем, если нам не требуется переопределять методы этой конструкции дженериками, мы можем даже объявить:

```luau
    export type class = object.class<typeof(class)>
```

И такая конструкция тоже верная, просто она не дает право переопределять поля, а при попытке сделать это через интерсекцию произойдет ошибка. Однако, почему же происходит проблема с наследованием при таком формате:

```luau
    local a = class.new() -- Node class, по цепи это object -> Disposable -> Node -> экземпляр Node
    a:get_initiate_event()
    local b = Disposable.new(class)
    a:beep(b)

    local r = setmetatable({},{__index=Disposable}) 
    type r = object.class<typeof(a)>

    class.new():beep(r) -- not ok
    class.new():beep(r :: r) -- not ok
    class.new():beep(b) -- ok
    class.new():beep(a) -- ok
```

Потому что здесь начинает работать не механизм `__index`, а структурная совместимость уже построенных типов. То есть, изначальная цепь наследования для `Node` построена через общий механизм построения в форме типа: `object -> Disposable -> Node` и сохраняется на протяжении всей цепи. Доказать, что `экземпляр Node & Node & Disposable & object` это один и тот же структурный объект, просто подвергшийся расширению - не составляет труда. Далее выполняется обычная структурная проверка:

"есть ли у этого типа всё, что требуется от Disposable?"

Ответ — да.

Теперь посмотрим на
```luau
local r = setmetatable({}, {
    __index = Disposable
})
```

Тип `r` — это `setmetatable<{}, {__index: typeof(Disposable)}>`. У него совершенно другая ситуация. С точки зрения типизатора собственная структура объекта — `{}`. Информация `__index = Disposable` не превращает его в структурный `Disposable`. __Именно это описывает `Issue #2219`.__

Всегда имейте ввиду: **типизатор никогда не использует `__index` как способ доказательства, это именно способ поиска недостающего значения в другом типе с обязательством проверки. Именно структурная типизация доказывает, что эти объекты совместимы, потому что внутри структур сигнатуры чаще всего совпадают, и это то что ожидается в языке.**

## Properly class creation

Теперь, зная, что к чему и почему, решением для создания ветви наследования является тривиальное:

В `object`:

```luau
    type base = typeof(class) -- естественно object
    export type class<that = {}, parent = base> = that & parent -- переставлены для удобства
```

```luau
    export type class = object.class<typeof(class)> -- если это первый наследник от линии object
    export type extend<T={}> = object.class<T,class> -- если это N наследник по линии
    export type class2 = extend<typeof(class2)>
```

Почему так? Да потому что все эти эксперименты, по сути своей, не отвечают на изначальный вопрос "как заставить классы наследники работать с классами прородителями и наоборот для внешнего наблюдателя и самих классов", а ответ тут очень банальный. До жути банальный.

```luau
    type correct = T0 & T1 & T2 & T3 & T4
```

Почему это работает? Потому что структуное сравнивание проверяет наличие нужных для конкретной сигнатуре структур. И неважно абсолютно, что эта струкута из себя представляет в этой `intersection`, потому что расскрывая все маски любой класс это буквально интерсекция метатаблицы и кучи таких же метатабличных типов. Проверка идет на наличие конкретной метатаблицы, а чем является `intersection` - соединением, которое валидно для всех перечисленных в нем типов. Поэтому класс наследник в 4 линии от изначального базового класса должен быть интерсекцией со своим родителем, а тот со своим и тот со своим до самой базы, - чтобы отвечать линии структурного наследования. Ей плевать на наличие лишних структур, она проверяет только то, что ей нужно.

## Hierarchical type inheritance

Возьмем в пример тот же класс, что и в примере `intersection` и с еще старым `object` типом `class`:

```luau
    local a = {}
    setmetatable(a, {__index = class})

    type a<T = {[string]: unknown}> = object.class<class<T>, typeof(a)>

    a.f = {}

    local function foo (t: a)

    end

    local r : class
    local d : a
    foo(r)
    foo(d)
```

Для всех участников в линейке интерсекций, как и в принципе для индексаторов тоже, тип `class` представляет собой обыкновенный экземпляр-расширитель. Для всех функций, которые его ожидают, применяется требование по проверке не соответствия типа 1 к 1, а на соответствие структур. Проверка проходит по ожидаемым значениям внутри: совпадения `{ [T]: U }`,

где `T` - ожидается синглтон-строка,
где `U` - ожидается одинаковая сигнатура между каждым значением, который указан на этот `T`

В данном примере на текущий момент времени проверка `r` через `foo(r)` вывовет ошибку. Это вызывается наличием совсем небольшой разницы между `class` и `a` даже несмотря ни на что - `.f` поле со значением таблицы. Такого поля нет ни в одной части наследуемой цепи `class`, а значит `foo()` будет отсекать неподходящих. Иначе, в примере с `d` - таког не происходит. То есть, класс родитель, пока разницы с наследником никакой нет, - совместим с ним в любом виде для стороннего наблюдателя. Если бы `foo()` была объявлена как функция внутри `a` - такое было бы также невозможно из-за самого факта существования `foo()` в `a`.

Если у `a` избавиться от разницы между `class`, убрав `.f`, - оба типа будут созаменимы.

Кроме того, generic типы созаменимы между собой, если стандартный `generic` имеет дефолтный `T = any`. То бишь, такое совместимо:

```luau
    type Signal<T = any> = {
        foo: () -> T
    }

    local function foo (a0: Signal) end
    local function bar (a1: Signal<number>)
    local T : Signal

    foo(T) -- correct
    bar(T) -- correct

    local U : Signal<string>

    foo(U) -- correct
    bar(U) -- invalid
```
