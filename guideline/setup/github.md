# Git

Если вы впервые работаете с системой контроля версий `git`, то данный раздел поможет понять каким образом ведется разработка проекта и каким образом следует взаимодействовать с удаленным репозиторием.

Все изменения должны производиться только внутри собственной рабочей ветки. Основная ветка проекта используется исключительно для хранения синхронизированной версии исходного кода.

Возникают вопросы? Обратитесь к другим участникам проекта.

## Clone

Перед началом работы необходимо клонировать репозиторий проекта в доступную и свободную вам папку. Вдальнейшем, работа будет вестись только с этой папкой.

```bash
git clone <repository>
```

После завершения клонирования рекомендуется убедиться, что репозиторий находится в актуальном состоянии.

```bash
git pull
```

## Branches

Перед началом выполнения любой задачи необходимо создать собственную ветку от актуальной `master`.

```bash
git checkout master
git pull
git checkout -b feature/my_changes
```

Название ветки рекомендуется выбирать таким образом, чтобы оно кратко описывало выполняемую задачу.

Во время работы запрещается выполнять изменения непосредственно в `master`.

## Status

Во время разработки рекомендуется регулярно проверять текущее состояние репозитория.

```bash
git status
```

Данная команда показывает:

* какие файлы были изменены;
* какие файлы были удалены;
* какие новые файлы были созданы;
* какие изменения уже подготовлены к коммиту.

## Add

После завершения логической части работы необходимые изменения следует добавить в индекс.

```bash
git add <file>
```

Либо добавить сразу все изменения.

```bash
git add .
```

Перед выполнением данной команды рекомендуется убедиться, что в индекс не попали временные файлы, настройки редактора или другие данные, не относящиеся к проекту.

## Commit

Коммит является сохранением текущего состояния изменений.

После подготовки файлов необходимо создать новый коммит.

```bash
git commit -m "Добавлено новое поведение Browser"
```

Каждый коммит должен описывать одно завершенное изменение. Не рекомендуется объединять несколько независимых задач в одном коммите.

## Pull

Перед отправкой изменений на сервер рекомендуется получить последние изменения из удаленного репозитория.

```bash
git pull origin master
```

Если во время получения изменений возник конфликт, его необходимо разрешить до продолжения работы.

## Push

После завершения работы изменения отправляются в собственную ветку.

```bash
git push origin feature/my_changes
```

После этого создается `Pull Request`, который будет рассмотрен во время проверки обновления.

## Merge conflicts

Во время совместной разработки несколько участников могут изменить один и тот же участок кода.

В таком случае `git` сообщит о конфликте слияния.

Необходимо вручную выбрать итоговую версию файла, сохранить изменения и выполнить новый коммит.

Конфликт считается разрешенным только после того, как все конфликтующие файлы были добавлены в индекс.

## Ignore

Файлы, не относящиеся к исходному коду проекта, должны находиться в `.gitignore`.

К таким файлам относятся:

* настройки редакторов;
* временные файлы;
* автоматически создаваемые каталоги;
* кэш различных инструментов.

Если подобные файлы были случайно добавлены в репозиторий, их необходимо удалить из индекса перед созданием коммита.

## History

Посмотреть историю изменений можно при помощи команды.

```bash
git log
```

Для более компактного отображения рекомендуется использовать.

```bash
git log --oneline
```

История коммитов позволяет определить, когда было внесено изменение и каким разработчиком оно было выполнено.

## General

Не отправляйте незавершенные изменения в общую ветку.

Не изменяйте историю уже опубликованных коммитов без предварительного согласования с остальными участниками разработки.

Если при выполнении задачи возникают сомнения относительно того, каким образом следует выполнить изменение, рекомендуется предварительно обсудить это с участниками проекта.
